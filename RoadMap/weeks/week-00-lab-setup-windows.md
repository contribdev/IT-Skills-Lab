# Неделя 0 (версия для Windows) — Лаборатория и рабочее окружение

**Исходные данные:** Windows-машина, 32 ГБ RAM.
**Короткий ответ: да, этого достаточно на весь план.** 32 ГБ — рабочий минимум для трёхнодовой лаборатории, и почти всё, что описано в 26 неделях, поместится. Узкие места появятся на неделях 14–15 (стек мониторинга) и 20–23 (AI-часть), и для них есть отдельные решения ниже.

**Время:** 7–9 часов.

---

## 📖 Часть 1. Выбор стратегии

### Что вообще нужно от лаборатории

По ходу плана понадобится:

| Требование | Когда | Что из этого следует |
|---|---|---|
| 3 отдельные машины с Linux | недели 2–8 | нужны настоящие ВМ, не контейнеры |
| Возможность выключать/перезагружать ноду | недели 2, 7, 8 | ВМ должны быть независимы |
| Стабильные IP-адреса | всегда | нужна нормальная сеть, а не NAT с плавающими адресами |
| Снапшоты и откат | всегда | точки возврата после экспериментов |
| Собрать кластер kubeadm с нуля | неделя 8 | ещё 3 ВМ (можно поочерёдно с основными) |
| Стек мониторинга | недели 14–15 | +3–4 ГБ RAM |
| GPU | недели 21–23 | аренда, локально не нужно |

Ключевой вывод: **Docker Desktop, kind и k3d не подойдут как основная лаборатория.** Они запускают «ноды» как контейнеры внутри одной виртуалки. Ты не сможешь выключить ноду, не сможешь чинить kubelet, не сможешь восстанавливать etcd и не увидишь настоящую межнодовую сеть. Половина заданий недель 5–8 потеряет смысл. Оставь kind как одноразовый инструмент для CI (он понадобится на неделе 11).

### Первое, что нужно проверить — редакция Windows

Открой PowerShell **от администратора**:

```powershell
systeminfo | Select-String "OS Name","OS Version"
```

Или просто `winver`.

| Твоя редакция | Рекомендуемый путь |
|---|---|
| **Windows 11/10 Pro, Enterprise, Education** | **Hyper-V** — путь A, оптимальный |
| **Windows 11/10 Home** | **VMware Workstation Pro** (бесплатна для личного использования) — путь B |

Заодно проверь, включена ли аппаратная виртуализация:

```powershell
systeminfo | Select-String "Hyper-V"
```

Если написано, что виртуализация в прошивке отключена — зайди в BIOS/UEFI и включи `Intel VT-x` / `AMD-V` (плюс `Intel VT-d` / `AMD IOMMU`, если есть). Без этого ничего не заработает.

## 📖 Часть 2. Три возможные конфигурации

### ✅ Путь A: Windows + Hyper-V + WSL2 (рекомендую)

```
┌────────────────────────────────────────────────────────┐
│ Windows 11 Pro (хост)                                  │
│                                                        │
│  Windows Terminal ──► WSL2 Ubuntu (рабочее место)       │
│                       kubectl, helm, k9s, git, ssh     │
│                       ~4 ГБ                            │
│                                                        │
│  Hyper-V:                                              │
│   ┌─────────┐  ┌─────────┐  ┌─────────┐                │
│   │  cp-1   │  │ node-1  │  │ node-2  │                │
│   │  4 ГБ   │  │  5 ГБ   │  │  5 ГБ   │                │
│   └─────────┘  └─────────┘  └─────────┘                │
│        └───── виртуальный коммутатор ─────┘            │
└────────────────────────────────────────────────────────┘
```

**Почему именно так:**

- Hyper-V — гипервизор первого типа, встроен в Windows, бесплатен, работает быстро и стабильно.
- **WSL2 и Hyper-V используют одну и ту же платформу виртуализации Windows и прекрасно уживаются.** Это критично: любой другой гипервизор (VirtualBox, старые VMware) с WSL2 конфликтует или теряет производительность.
- WSL2 даёт тебе **настоящий Linux-шелл** как рабочее место: `kubectl`, `helm`, `bash`-скрипты, `ssh`, автодополнение — всё работает как на Linux-машине. Ты получаешь Linux-опыт без переустановки системы.
- Docker Desktop (если понадобится) тоже работает на WSL2-бэкенде и не конфликтует.

**Минусы:** только Pro-редакция; включение Hyper-V чуть замедляет игры (Windows начинает работать поверх гипервизора).

### ✅ Путь B: Windows Home + VMware Workstation Pro

С 2024 года **VMware Workstation Pro бесплатна для личного использования**. Это полноценный гипервизор второго типа с отличными снапшотами и удобным управлением сетями.

⚠️ Важный нюанс: VMware Workstation умеет работать одновременно с включённой платформой Windows Hypervisor (то есть с WSL2), но при этом **теряет производительность** — VMware переходит в режим работы поверх Hyper-V. Варианты:

1. **Оставить WSL2 включённым** и смириться с некоторой потерей скорости ВМ. Для лаборатории обычно приемлемо.
2. **Отключить WSL2** и использовать в качестве рабочего места отдельную маленькую Linux-ВМ во VMware. Быстрее, но менее удобно.

Я бы выбрал первый вариант — удобство рабочего окружения важнее нескольких процентов производительности ВМ.

**VirtualBox** как вариант тоже существует, но он проигрывает VMware по производительности и стабильности работы с вложенной виртуализацией. Бери его, только если VMware по какой-то причине не подходит.

### ⚪ Путь C: отдельная машина с Proxmox

Если у тебя есть (или можно недорого купить) второй компьютер — старый десктоп, мини-ПК, б/у офисная машина на 32 ГБ — это **лучший вариант в долгую**:

- лаборатория работает круглосуточно, не мешая основной машине
- доступ по SSH откуда угодно, в том числе с работы и с ноутбука
- на неделе 22 можно воткнуть GPU и получить свой inference-сервер
- ты получаешь опыт работы с Proxmox — это плюс сам по себе

Но начинать ради этого покупку железа не нужно. Начни с пути A, а к 4–5 месяцу решишь, стоит ли выносить лабораторию на отдельную коробку.

### ❌ Чего делать не стоит

**Не ставь Linux вторым системным разделом ради этого плана.** Причины:

- Дуалбут создаёт трение: чтобы позаниматься 40 минут, нужно перезагрузиться и выйти из рабочего контекста. На третьем месяце это станет причиной пропущенных недель.
- WSL2 закрывает 90% потребности в Linux-опыте: тот же шелл, те же утилиты, тот же пакетный менеджер.
- Ноды в лаборатории и так на Linux — ты будешь работать с ним каждый день по SSH.

Если очень хочется перейти на Linux как основную систему — это разумное решение само по себе, но принимай его отдельно от учебного плана и **не в первую неделю**. Переезд ОС + новый предмет одновременно — верный способ утонуть в настройке окружения вместо учёбы.

**Не пытайся сделать «ноды» из нескольких дистрибутивов WSL2.** Все дистрибутивы WSL2 живут внутри одной служебной виртуальной машины и делят её сетевой стек. Многонодового кластера из этого не получится.

## 📖 Часть 3. Бюджет памяти — честный расчёт

32 ГБ — это не 32 ГБ доступных. Реальная раскладка:

| Потребитель | Сколько |
|---|---|
| Windows + фоновые службы | 3–4 ГБ |
| Браузер (10–15 вкладок документации) | 3–4 ГБ |
| IDE / редактор | 1–2 ГБ |
| WSL2 (ограничим явно) | 4 ГБ |
| **Остаётся на ВМ** | **≈ 18–20 ГБ** |

Отсюда стартовая конфигурация:

| ВМ | vCPU | RAM | Диск |
|---|---|---|---|
| cp-1 | 2 | 4 ГБ | 40 ГБ |
| node-1 | 2 | 5 ГБ | 40 ГБ |
| node-2 | 2 | 5 ГБ | 40 ГБ |
| **Итого** | | **14 ГБ** | 120 ГБ |

Остаётся запас 4–6 ГБ — он понадобится на неделе 8, когда будешь параллельно поднимать kubeadm-кластер.

### Что делать, когда станет тесно

Тесно станет на неделях 14–15 (Prometheus + Grafana + Loki съедают 3–4 ГБ) и на неделе 20 (Qdrant + RAG-сервис).

Варианты по возрастанию стоимости:

1. **Выключай ненужное.** Не держи одновременно основной кластер и kubeadm-кластер. Между блоками останавливай ВМ.
2. **Сократи до 2 нод** временно: cp-1 + node-1 с 8 ГБ. Для Helm/ArgoCD/мониторинга этого хватает.
3. **Ограничь аппетиты стека мониторинга:** короткий retention Prometheus (3–5 дней), урезанные ресурсы в values чарта. Это, кстати, полезное упражнение само по себе.
4. **Докупи память.** Если у тебя DDR4 и свободные слоты — 32 ГБ докупить стоит недорого и это самое результативное вложение в лабораторию. 64 ГБ снимают вопрос до конца плана.
5. **Вынеси часть в облако.** На неделе 16 ты всё равно будешь поднимать managed-кластер в облаке через Terraform — можно оставить его на пару недель под тяжёлые эксперименты (следи за расходом гранта).

### Диск

- Только **SSD/NVMe**. На HDD лаборатория превращается в мучение.
- Заложи **200 ГБ** свободного места: 120 ГБ под ВМ, остальное под снапшоты и образы контейнеров (они копятся быстрее, чем кажется).
- Используй динамически расширяющиеся диски (VHDX в Hyper-V — по умолчанию такие).

## 🔧 Задание 1 (путь A): включаем Hyper-V и WSL2 (1 ч)

### Hyper-V

PowerShell от администратора:

```powershell
Enable-WindowsOptionalFeature -Online -FeatureName Microsoft-Hyper-V -All
```

Перезагрузись. Затем открой **Диспетчер Hyper-V** (`virtmgmt.msc`).

### WSL2

```powershell
wsl --install -d Ubuntu-24.04
wsl --set-default-version 2
wsl --status
```

Ограничь ресурсы WSL2 — иначе он со временем съедает всё, до чего дотянется. Создай файл `C:\Users\<ты>\.wslconfig`:

```ini
[wsl2]
memory=4GB
processors=4
swap=2GB
localhostForwarding=true

[experimental]
autoMemoryReclaim=gradual
sparseVhd=true
```

Примени: `wsl --shutdown`, затем снова запусти Ubuntu.

⚠️ `autoMemoryReclaim` и `sparseVhd` заметно улучшают поведение WSL2 на долгой дистанции — WSL склонен не отдавать память и раздувать свой виртуальный диск.

### Windows Terminal

Поставь из Microsoft Store (в Windows 11 уже есть). Сделай профиль Ubuntu профилем по умолчанию. Дальше вся работа — оттуда.

## 🔧 Задание 2 (путь A): сеть Hyper-V (1 ч)

Это самая нетривиальная часть на Windows — читай внимательно.

### Проблема Default Switch

Hyper-V из коробки предлагает **Default Switch** — NAT, при котором подсеть **меняется после каждой перезагрузки хоста**. Для лаборатории, где IP-адреса нод прописаны в конфигах, kubeconfig и сертификатах, это катастрофа: после перезагрузки Windows кластер просто развалится.

**Никогда не используй Default Switch для кластера.**

### Решение 1: External switch (рекомендую, если хост подключён по кабелю)

ВМ получают адреса из твоей домашней сети наравне с остальными устройствами. Просто, стабильно, ВМ доступны с других устройств.

Диспетчер Hyper-V → Диспетчер виртуальных коммутаторов → Создать → **Внешняя** → выбери физический адаптер Ethernet → OK.

Затем на роутере закрепи IP по MAC-адресам ВМ (или задай статические адреса внутри ВМ).

⚠️ С Wi-Fi адаптером External switch работает, но капризно (проблемы с MAC-спуфингом на некоторых адаптерах). Если хост на Wi-Fi — иди по решению 2.

### Решение 2: Internal switch + собственный NAT (универсально)

Своя изолированная подсеть с фиксированной адресацией, работает независимо от того, как подключён хост.

```powershell
# Создать внутренний коммутатор
New-VMSwitch -SwitchName "k8s-lab" -SwitchType Internal

# Найти индекс появившегося интерфейса
Get-NetAdapter | Where-Object Name -like "*k8s-lab*"

# Назначить хосту адрес шлюза (подставь свой ifIndex)
New-NetIPAddress -IPAddress 192.168.100.1 -PrefixLength 24 -InterfaceIndex <ifIndex>

# Включить NAT для выхода ВМ в интернет
New-NetNat -Name "k8s-lab-nat" -InternalIPInterfaceAddressPrefix 192.168.100.0/24
```

⚠️ Одновременно может существовать только один `NetNat` с пересекающимся префиксом. Если команда ругается — посмотри `Get-NetNat`, возможно, там уже что-то есть (часто от Docker Desktop или WSL).

Итоговая адресация — запиши её, она будет встречаться весь план:

| Хост | IP | Роль |
|---|---|---|
| Windows (шлюз) | 192.168.100.1 | хост |
| cp-1 | 192.168.100.11 | k3s server |
| node-1 | 192.168.100.12 | k3s agent |
| node-2 | 192.168.100.13 | k3s agent |

### Доступ из WSL2

WSL2 живёт за своим NAT и по умолчанию **не видит** подсеть Hyper-V напрямую. Проверь:

```bash
ping 192.168.100.11
```

Если не проходит, варианты:

1. **Windows 11 + WSL2 в зеркальном режиме** — самое чистое решение. В `.wslconfig`:
   ```ini
   [wsl2]
   networkingMode=mirrored
   ```
   WSL начинает использовать сетевые интерфейсы Windows напрямую и видит всё, что видит хост.

2. **Маршрут вручную** (если зеркальный режим недоступен) — добавить маршрут в WSL к подсети лаборатории через шлюз Windows.

3. **Работать через SSH-туннель**: обращаться к API-серверу через `ssh -L 6443:localhost:6443 cp-1`. Рабочий, но неудобный вариант.

Не пропускай этот шаг: без доступа из WSL2 придётся работать через PowerShell, а это заметно хуже.

## 🔧 Задание 3: создаём эталонную ВМ и клонируем (2 ч)

### Скачай образ

Ubuntu Server 24.04 LTS, ISO для amd64.

### Создай первую ВМ (Hyper-V)

**Обязательно: поколение 2** (UEFI, современный вариант).

```powershell
New-VM -Name "cp-1" -MemoryStartupBytes 4GB -Generation 2 `
  -NewVHDPath "D:\HyperV\cp-1.vhdx" -NewVHDSizeBytes 40GB -SwitchName "k8s-lab"

Set-VM -Name "cp-1" -ProcessorCount 2 -StaticMemory
Set-VMFirmware -VMName "cp-1" -EnableSecureBoot Off      # важно для Ubuntu
Add-VMDvdDrive -VMName "cp-1" -Path "D:\iso\ubuntu-24.04-live-server-amd64.iso"
```

⚠️ **`-StaticMemory` — важно.** Динамическая память Hyper-V «раздувает» и «сдувает» объём на лету, а kubelet определяет доступную память при старте и считает её постоянной. С динамической памятью ты получишь неверный `Allocatable`, странные вытеснения подов и невоспроизводимые эксперименты с ресурсами (недели 3 и 7). Для лаборатории по Kubernetes память должна быть статической.

⚠️ **Отключи Secure Boot** или выбери шаблон `MicrosoftUEFICertificateAuthority` — иначе Ubuntu не загрузится.

### Установка Ubuntu

Минимальная установка, обязательно поставь OpenSSH Server. Пользователя назови одинаково на всех нодах.

### Подготовка (на эталонной ВМ, до клонирования)

```bash
# Обновление
sudo apt update && sudo apt upgrade -y
sudo apt install -y curl vim net-tools

# Отключить swap — требование Kubernetes
sudo swapoff -a
sudo sed -i '/ swap / s/^/#/' /etc/fstab

# Модули ядра
cat <<EOF | sudo tee /etc/modules-load.d/k8s.conf
overlay
br_netfilter
EOF
sudo modprobe overlay && sudo modprobe br_netfilter

# sysctl
cat <<EOF | sudo tee /etc/sysctl.d/k8s.conf
net.bridge.bridge-nf-call-iptables  = 1
net.bridge.bridge-nf-call-ip6tables = 1
net.ipv4.ip_forward                 = 1
EOF
sudo sysctl --system

# Интеграция с Hyper-V (обычно уже есть в Ubuntu Server)
sudo apt install -y linux-tools-virtual linux-cloud-tools-virtual
```

### Статический IP

Ubuntu 24.04 использует netplan. Отредактируй `/etc/netplan/50-cloud-init.yaml`:

```yaml
network:
  version: 2
  ethernets:
    eth0:
      dhcp4: false
      addresses: [192.168.100.11/24]
      routes:
        - to: default
          via: 192.168.100.1
      nameservers:
        addresses: [8.8.8.8, 1.1.1.1]
```

```bash
sudo chmod 600 /etc/netplan/50-cloud-init.yaml
sudo netplan apply
```

⚠️ Имя интерфейса может отличаться (`eth0`, `ens160`) — проверь через `ip a`.

### Клонирование

Выключи ВМ, экспортируй, импортируй дважды с копированием (новые идентификаторы):

```powershell
Stop-VM -Name "cp-1"
Export-VM -Name "cp-1" -Path "D:\HyperV\export"

Import-VM -Path "D:\HyperV\export\cp-1\Virtual Machines\<GUID>.vmcx" `
  -Copy -GenerateNewId -VirtualMachinePath "D:\HyperV\node-1" `
  -VhdDestinationPath "D:\HyperV\node-1"
# повторить для node-2, затем переименовать через Rename-VM
```

**На каждом клоне обязательно:**

```bash
sudo hostnamectl set-hostname node-1
sudo rm -f /etc/machine-id && sudo systemd-machine-id-setup
# поправить IP в netplan
sudo reboot
```

⚠️ **Одинаковый `machine-id` на нодах — источник плавающих, необъяснимых проблем.** Не пропускай эту команду.

### Контрольные точки

После того как всё поднялось, сделай контрольные точки всех трёх ВМ:

```powershell
Checkpoint-VM -Name "cp-1" -SnapshotName "clean-ubuntu"
```

⚠️ **Останавливай ВМ перед созданием контрольной точки.** Снимок работающей машины сохраняет состояние памяти, и при откате часы внутри ВМ окажутся в прошлом — а это ломает TLS-сертификаты и работу etcd. Симптом («сертификат ещё не действителен») выглядит загадочно и съедает часы отладки. Правило: остановил → снимок → запустил.

## 🔧 Задание 4: k3s (1 ч)

Дальше всё как в основной методичке — работай из WSL2 по SSH.

```bash
ssh-keygen -t ed25519
ssh-copy-id user@192.168.100.11    # и на остальные ноды
```

**На cp-1:**
```bash
curl -sfL https://get.k3s.io | INSTALL_K3S_EXEC="--write-kubeconfig-mode 644 \
  --disable traefik --node-name cp-1 \
  --tls-san 192.168.100.11" sh -

sudo cat /var/lib/rancher/k3s/server/node-token
```

⚠️ `--tls-san` с IP control-plane обязательно, иначе при обращении с рабочей машины получишь ошибку проверки сертификата.

**На node-1 и node-2:**
```bash
curl -sfL https://get.k3s.io | K3S_URL=https://192.168.100.11:6443 \
  K3S_TOKEN="<токен>" INSTALL_K3S_EXEC="--node-name node-1" sh -
```

**В WSL2:**
```bash
mkdir -p ~/.kube
scp user@192.168.100.11:/etc/rancher/k3s/k3s.yaml ~/.kube/config-lab
sed -i 's/127.0.0.1/192.168.100.11/' ~/.kube/config-lab
chmod 600 ~/.kube/config-lab
export KUBECONFIG=~/.kube/config-lab

kubectl get nodes -o wide
kubectl label node node-1 node-2 node-role.kubernetes.io/worker=worker
```

## 🔧 Задание 5: рабочее окружение в WSL2 (1 ч)

```bash
# kubectl
curl -LO "https://dl.k8s.io/release/$(curl -Ls https://dl.k8s.io/release/stable.txt)/bin/linux/amd64/kubectl"
sudo install -o root -g root -m 0755 kubectl /usr/local/bin/kubectl

# helm
```

## 🔧 Задание 6: настройки Windows, без которых будет больно (0.5 ч)

1. **Исключения антивируса.** Добавь папку с VHDX-файлами и каталог WSL в исключения Microsoft Defender. Постоянное сканирование файлов виртуальных дисков — одна из главных причин тормозов лаборатории.
   ```powershell
   Add-MpPreference -ExclusionPath "D:\HyperV"
   ```

2. **Отключи сон и гибернацию.** Уход хоста в сон роняет кластер: ноды теряют связь, etcd видит скачок времени.
   ```powershell
   powercfg /change standby-timeout-ac 0
   powercfg /change hibernate-timeout-ac 0
   ```

3. **Отложи автоматические перезагрузки Windows Update** — иначе однажды придёшь к развалившемуся кластеру посреди эксперимента.

4. **Автозапуск ВМ:** реши, должны ли ноды подниматься вместе с Windows.
   ```powershell
   Set-VM -Name "cp-1" -AutomaticStartAction Start -AutomaticStartDelay 0
   Set-VM -Name "node-1" -AutomaticStartAction Start -AutomaticStartDelay 30
   ```
   Задержка важна: агенты должны стартовать после control-plane.

5. **Корректное завершение:** `Set-VM -AutomaticStopAction ShutDown` — чтобы при перезагрузке Windows ВМ выключались штатно, а не «сохранялись» (сохранение состояния = скачок времени при возврате).

## Что делать, если что-то пошло не так

| Симптом | Вероятная причина |
|---|---|
| ВМ не создаётся, ошибка про виртуализацию | VT-x/AMD-V выключен в BIOS, либо конфликт с другим гипервизором |
| Ubuntu не загружается с ISO | не отключён Secure Boot, либо создано поколение 1 вместо 2 |
| ВМ не видит интернет | не создан NetNat, или неверный шлюз в netplan |
| Из WSL2 не пингуются ноды | нужен зеркальный режим сети WSL или маршрут вручную |
| `kubectl` ругается на сертификат | забыт `--tls-san` с IP control-plane |
| Ноды случайно становятся NotReady | хост уходил в сон; либо динамическая память; либо одинаковый `machine-id` |
| Всё дико тормозит | VHDX не в исключениях антивируса; либо диск не SSD; либо ВМ на `/mnt/c` |
| После отката снапшота кластер сломан | снимок был сделан на работающей ВМ, часы ушли назад |
