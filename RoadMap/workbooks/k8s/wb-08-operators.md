Жизненный цикл stateless приложений в k8s полностью автоматизирован:
-создаёт реплики при сбоях; 
-перезапускает модули с новой версией образа; 
-сопоставляет фактическое состояние приложений с желаемым, которое задаётся в конфигурационных файлах

Но в statefull (например бд) приложениях так не работает, у каждой реплики свое состояние и идентичность.
Их нужно:
-обновлять и уничтожать в определённом порядке
-синхронизировать между собой
-учитывать особенности конкретного приложения (MySQL, Postgres, Elasticsearch и т. д.)

Из‑за этого требуется ручное вмешательство — что противоречит концепции автоматизации в Kubernetes

Kubernetes Operator (оператор в Kubernetes) — это программный компонент, который расширяет возможности платформы для управления сложными приложениями и их жизненным циклом. Он позволяет инкапсулировать знания о том, как правильно разворачивать, обновлять, масштабировать и обслуживать конкретное приложение, делая это как будто это нативное встроенное в Kubernetes средство. 

Оператор состоит из двух ключевых компонентов:
-Custom Resource Definition (CRD) — расширяет API Kubernetes, определяя новый тип ресурса, который пользователь может создавать в кластере. В этом ресурсе декларативно описывается желаемое состояние приложения (Spec), а также может храниться фактическое состояние (Status).
-Контроллер — это программный цикл, который постоянно наблюдает за экземплярами CRD. Его задача — реализовать цикл управления (control loop), постоянно сравнивая фактическое состояние с желаемым и приводя их в соответствие (паттерн Reconcile: Observe → Create → Correct → Report). Если что-то пошло не так (например, pod вышел из строя или конфигурация изменилась), контроллер выполняет необходимые действия: создаёт недостающие ресурсы, обновляет приложение, делает бэкапы, масштабирует.

Примеры задач, которые операторы автоматизируют:
-Развёртывание и управление кластерами баз данных (PostgreSQL, Redis, Kafka). 
-Создание и восстановление резервных копий. 
-Обновление приложения с учётом изменений в схеме базы данных или конфигурациях. 
-Автоматическое масштабирование в зависимости от нагрузки. 
-Управление сертификатами (например, через cert-manager). 
-Развёртывание и управление сервисными mesh (например, Istio). 

В экосистеме Kubernetes есть множество готовых операторов:
-Postgres Operator — управляет кластерами PostgreSQL.
-Prometheus Operator — упрощает настройку мониторинга.
-Elastic Kubernetes Operator — автоматизирует развёртывание Elastic Search и Kibana.
-Strimzi — оператор для управления кластерами Kafka.
-cert-manager — автоматизирует управление SSL/TLS.


Полезное: CloudNativePG
Три Service создаёт operator

| Service | Назначение |
|---|---|
| `postgres-rw` | Только primary (read-write) — **сюда подключается приложение** |
| `postgres-ro` | Только replicas (read-only) |
| `postgres-r` | Любой instance (балансировка) |

Зачем три, а не один
Проблема: в PostgreSQL только primary принимает запись (INSERT, UPDATE, DELETE). Replicas — только чтение (SELECT).

Если приложение всегда подключается к одному Service — оно не знает, primary там сейчас или replica. А после failover primary меняется — приложение пишет в replica — ошибка.

Решение: CNPG создаёт три Service с разными ролями.

Приложение-писатель всегда подключается к -rw. После failover operator обновляет Endpoints этого Service — теперь он указывает на новый primary. Приложение не замечает смены.

Приложение-читатель подключается к -ro. Запросы распределяются между всеми replicas. Primary не нагружается чтением.

Failover — автоматическое переключение с упавшего primary на здоровую replica. Replica повышается до primary, приложение продолжает работать.
Как это работает в CNPG
1. Мониторинг. CNPG-operator постоянно проверяет здоровье pod'ов. Если primary не отвечает N секунд — начинает failover.

2. Выбор кандидата. Из всех replicas выбирается самая свежая (по LSN — Log Sequence Number). Это минимизирует потерю данных.

3. Promotion. Кандидат повышается:
postgres-rw → postgres-2 (новый primary)

Приложение не замечает. Подключение по postgres-rw.database.svc.cluster.local всё ещё работает — просто указывает на другой pod.
Failover ≠ backup. Если оба pod'а упадут одновременно — данные потеряются (если нет backup в S3). CNPG умеет делать backup — но это отдельная настройка (spec.backup).

Failover ≠ защита от human error. Если ты случайно сделаешь DROP TABLE — это реплицируется на replica мгновенно. Failover не поможет — данные удалены везде.

Для защиты от human error — PITR (Point-In-Time Recovery) из backup. Отдельная тема.
