Argo CD — это декларативный инструмент непрерывной доставки (Continuous Delivery) для Kubernetes, реализующий паттерн GitOps .

Ключевая идея GitOps: Git-репозиторий является единственным источником правды для описания желаемого состояния приложения. Всё, что должно быть в кластере, описано в Git. Argo CD следит за этим описанием и автоматически приводит кластер к нужному состоянию .

Зачем это нужно:

Аудит: каждое изменение проходит через Git, видно кто, что и когда поменял.
Автоматизация: не нужно вручную применять kubectl apply — Argo CD сделает это сам.
Самовосстановление: если кто-то вручную изменил ресурс в кластере, Argo CD вернёт его к состоянию из Git 

Argo CD работает как Kubernetes-контроллер, который постоянно сравнивает два состояния:
Желаемое состояние (Desired State) — то, что описано в Git-репозитории (YAML, Helm, Kustomize).
Текущее состояние (Live State) — то, что реально работает в кластере.

Если они расходятся — приложение помечается как OutOfSync. Argo CD может автоматически или вручную синхронизировать кластер с Git .
Цикл работы:

Git (желаемое)  ←→  Argo CD (сравнивает)  ←→  Кластер (текущее)
                         │
                         ├── Synced (всё совпадает)
                         └── OutOfSync (есть расхождения)

Возможные схемы реализации

1) Один argoCD для нескольких кластеров
Плюсы:
-Один Argo CD — меньше инфраструктуры.
-Единая точка управления всеми окружениями.
-Легко добавлять новые кластеры.

Минусы:
-Shared Cluster становится single point of failure.
-Если он упадёт — деплой в оба окружения остановится.
-Нужно обеспечить сетевую связность между кластерами.


2) На каждый кластер свой argoCD

Плюсы:
-Изоляция. Падение Argo CD в dev не влияет на prod, и наоборот.
-Нет single point of failure. Если один кластер недоступен — второй продолжает работать.
-Проще сеть. Не нужно, чтобы центральный Argo CD имел доступ к обоим кластерам. Каждый Argo CD работает локально.
-Безопасность. Prod-кластер не зависит от внешнего Argo CD, который может быть скомпрометирован.
-Естественные границы. Dev и prod — разные команды, разные права, разные кластеры.

Минусы:
-Дублирование инфраструктуры. Два Argo CD — вдвое больше ресурсов, обновлений, мониторинга.
-Сложнее управлять конфигурацией. Нужно синхронизировать версии Argo CD между кластерами.
-Сложнее видеть общую картину. Чтобы посмотреть статус обоих окружений, нужно зайти в оба Argo CD.
-Дублирование Application-манифестов. Каждый Argo CD должен знать про свои приложения — либо через Git, либо через ручную настройку.
-RBAC сложнее. Пользователи должны иметь доступ к обоим Argo CD.

Application — это центральный объект Argo CD. Он описывает связь между источником (Git) и назначением (кластер + namespace) .

apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: my-app
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/org/repo
    targetRevision: main
    path: apps/my-app
  destination:
    server: https://kubernetes.default.svc
    namespace: my-app
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
      
Ключевые поля:
-source.repoURL — Git-репозиторий.
-source.path — путь к манифестам внутри репозитория.
-source.targetRevision — ветка, тег или коммит.
-destination.server — адрес кластера (https://kubernetes.default.svc — текущий кластер).
-destination.namespace — куда деплоить
